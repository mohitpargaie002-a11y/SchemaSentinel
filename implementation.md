# SchemaSentinel — Implementation Plan

**Working title:** SchemaSentinel  
**One-line product:** An approval-gated agent that investigates, tests, explains, and safely applies database schema changes.  
**Hackathon:** The Agent Harness Hackathon 2026, WeMakeDevs × TrueFoundry  
**Hackathon window:** Aug 24–30, 2026  
**Primary target:** Best Use of TrueForge  
**Secondary targets:** Best UI, Best Code Quality  
**Status:** Day 1 implementation plan locked. Coding may begin now.

---

## 0. Executive Decision

### Product name

**SchemaSentinel** is the preferred name. It communicates database/schema safety without sounding like a generic SQL chatbot.

Possible marketing line:

> **SchemaSentinel — Let the agent test the migration before you trust the migration.**

Backup names, if needed later: MigrationGuard, SchemaSentry, SafeDDL.

### The single job

SchemaSentinel receives a proposed database change and takes it through a controlled lifecycle:

```text
User request / migration
        ↓
Understand schema + change
        ↓
Plan
        ↓
Inspect dependencies and risk
        ↓
Generate or validate migration
        ↓
Run candidate migration in isolated sandbox
        ↓
Run integrity / regression checks
        ↓
Prepare human-readable risk report
        ↓
STOP FOR HUMAN APPROVAL
        ↓
Apply approved migration to an owned staging/demo database
        ↓
Verify schema + application invariants
        ↓
Produce final audit record
```

The agent, not a normal chat wrapper, must perform the work. TrueForge must visibly orchestrate real MCP tools, sandbox execution, human approval, and session state. The hackathon brief explicitly requires the harness to do real work and stop before an irreversible action. [Hackathon brief: requirements and judging](https://www.wemakedevs.org/hackathons/trueforge/rules)

# 1. Hackathon Strategy

## 1.1 What the judges reward

The hackathon has six equally weighted judging criteria:

1. Potential impact
2. Creativity and originality
3. Technical excellence
4. Use of sponsor tools
5. Control and safety
6. Presentation

The sponsor track for Best Use of TrueForge specifically emphasizes real MCP tools, generated code in a sandbox, human approval before irreversible actions, subagents, and persistent sessions. The Best UI track expects the user to see what the agent is doing, waiting for, and has already done. The Best Code Quality track requires Qodo to be installed early and pull requests reviewed throughout the build. [Hackathon brief](https://www.wemakedevs.org/hackathons/trueforge/rules)

## 1.2 Why SchemaSentinel is designed this way

Schema changes are a natural irreversible action. They also provide a clean, understandable agent loop:

```text
Inspect → Test → Explain → Ask → Apply → Verify
```

The demo can therefore make the safety boundary obvious instead of inventing a theatrical confirmation dialog.

## 1.3 Non-goals

Do not expand the MVP into:

- a general SQL copilot
- a general database admin platform
- an incident-response platform
- a generic code-review agent
- an automatic production migration service
- a multi-cloud database control plane
- a broad DevOps dashboard

One narrow job, completed end to end, is the priority.

# 2. Product Scope

## 2.1 MVP input modes

Support two entry modes:

### A. Migration file

User supplies a `.sql` migration or a migration file generated by the agent.

Example:

```sql
ALTER TABLE orders
ADD COLUMN fulfillment_status VARCHAR(32) NOT NULL DEFAULT 'pending';
```

### B. Natural-language request

Example:

> “Add an indexed customer status to orders and make existing records default to `active`.”

SchemaSentinel converts the request into a proposed migration, then subjects it to the same safety pipeline.

## 2.2 MVP database target

Use PostgreSQL only for the first version.

Use an **owned demo/staging PostgreSQL database** for the final irreversible action. Never connect to an unknown third-party production database.

Recommended setup:

- Local/disposable PostgreSQL or PGlite for fast sandbox tests.
- One dedicated Neon/Supabase PostgreSQL database for the final “approved apply” demonstration.
- Separate database/schema names for sandbox vs approved target.

The hackathon rules require tools, data, and accounts to be owned or authorized by the participant. Never place real credentials in the repository or demo. [Hackathon rules](https://www.wemakedevs.org/hackathons/trueforge/rules)

## 2.3 MVP outputs

Every run should produce:

- migration plan
- detected schema dependencies
- risk level
- affected tables/columns/indexes
- sandbox execution result
- integrity test results
- rollback/compensation assessment
- exact SQL that will be applied after approval
- approval decision
- final verification result
- session/audit timeline

# 3. Golden Demo Scenario

The primary demo must be deterministic and finish quickly.

## Scenario

Start from a realistic Postgres database containing:

- `users`
- `orders`
- `order_items`
- `payments`
- realistic row counts simulated with seed data
- existing indexes and constraints

User asks:

> “Add `status` to orders and make it searchable.”

A deliberately risky candidate migration is supplied or generated.

SchemaSentinel should discover something such as:

- existing table is large
- naive DDL could rewrite/lock the table
- index creation approach is suboptimal
- backfill could cause excessive write load

The agent then proposes a safer staged migration.

### Demo result

```text
Migration: 0042_add_order_status.sql

Risk: HIGH → MEDIUM after remediation
Affected table: orders
Estimated rows: 2.4M
Potential lock: HIGH for naive approach
Rollback test: PASS
Integrity checks: PASS

Safer plan:
1. Add nullable column
2. Backfill in batches
3. Add index using safe strategy
4. Enforce constraint after backfill
5. Remove legacy path in a later migration

[Reject] [Approve & Apply]
```

Clicking **Approve & Apply** is the irreversible boundary.

Then the agent applies the approved plan and runs verification.

- agent execution loop
- model calls
- MCP tool execution
- approval checkpoints

### SchemaSentinel application

Owns:

- product UI

- risk report rendering
- scenario configuration
- audit presentation
- deterministic validation rules
- allowed target configuration

### MCP layer

Minimum MCP tools:

1. **GitHub MCP**
   - inspect repository
   - read migration files
   - inspect PR context
   - create PR / comment

2. **Postgres MCP**
   - inspect schemas
   - inspect tables/indexes/constraints
   - execute read-only diagnostics
   - run approved migration against the owned target

3. **Optional Demo/Runner MCP**
   - initialize seed database
   - reset disposable target
   - run application-level smoke checks

Prefer existing trustworthy MCP servers over writing custom wrappers unless the required operation is genuinely missing.

# 5. Agent Responsibilities

## 5.1 Main agent

The main SchemaSentinel agent owns the lifecycle:

```text
UNDERSTAND
→ INSPECT
→ PLAN
→ TEST
→ ASSESS
→ REPORT
→ APPROVE
→ APPLY
→ VERIFY
```

It should never skip the safety gate for an irreversible target mutation.

## 5.2 Subagents

Use TrueForge subagents for genuinely separable work. Suggested initial roles:

### Schema Analyst

Responsibilities:

- understand current schema
- find dependencies
- identify affected objects
- identify indexes and constraints

### Migration Risk Analyst

Responsibilities:

- detect destructive DDL
- identify potentially blocking operations
- flag unsafe backfills
- check compatibility risks

### Sandbox Validator

Responsibilities:

- execute candidate migration in isolated database
- run integrity tests
- capture timings/errors
- test rollback/compensation where meaningful

### Review Synthesizer

Responsibilities:

- merge findings
- generate final risk summary
- produce approval packet

Do not create subagents merely to make the architecture look sophisticated. Each must own a meaningful piece of work.

# 10. Safety Architecture

## 10.1 Hard rules

The agent must never:

- connect to arbitrary databases supplied by the user
- apply arbitrary SQL to an unapproved target
- skip sandbox validation for the MVP
- execute destructive operations without a TrueForge approval checkpoint
- fabricate a successful validation result
- claim rollback success without performing it
- expose credentials in logs/UI

## 10.2 Target allowlist

Use an explicit target registry:

```text
TARGET_ID = demo-postgres
TARGET_ENV = staging-demo
```

The UI does not accept arbitrary connection strings.

## 10.3 Tool permissions

Classify tools:

### Read-only

- inspect schema
- inspect indexes
- inspect constraints
- read migration files

### Sandbox write

- generate SQL
- create temporary tables/data
- run tests

### Irreversible / controlled

- apply migration to approved target
- destructive cleanup

Only the last category must be behind explicit approval.

## 10.4 Code Mode

If TrueForge Code Mode is used, test its destructive-tool behavior carefully. An August 2026 TrueForge issue reports edge cases around destructive-tool annotations in Code Mode. Do not rely on annotations alone; retain explicit tool-level allowlists and approval gates in our own application design. [TrueForge issue #318](https://github.com/truefoundry/trueforge/issues/318)

# 11. Sandbox Strategy

The sandbox is one of the most important judging surfaces.

## Candidate execution model

Generated migration artifacts should be written into the TrueForge sandbox:

```text
/workspace/
├── migration.sql
├── before_schema.sql
├── after_schema.sql
├── seed.sql
├── validation.sql
└── report.json
```

The agent then executes deterministic checks against the disposable database.

## Validation checks

Minimum:

- migration executes
- expected objects exist
- existing constraints remain valid
- representative reads still work
- representative writes still work
- indexes exist where expected
- nullability/default behavior is correct
- rollback/compensation path is tested where applicable

## PGlite vs PostgreSQL

Use PGlite for cheap deterministic unit/integration tests.

Use a disposable real PostgreSQL database for the strongest end-to-end demo validation when practical.

Do not claim PGlite proves production PostgreSQL locking behavior. Where lock behavior matters, the risk report must clearly state that it is a static/heuristic assessment unless measured on real PostgreSQL.

## github.create_pr

# 13. Approval Model

The central rule:

> **The agent may investigate and prepare the change autonomously, but the irreversible database mutation requires explicit approval.**

Approval should be a real TrueForge checkpoint, not an application-only button pretending the harness approved something.

Approval payload should bind:

- session ID
- migration plan ID
- target ID
- plan checksum/hash
- generated SQL hash
- risk level
- timestamp

If the migration changes after approval, invalidate the approval and require a new one.

# 14. Session / Reconnect Behavior

This is a sponsor-feature opportunity.

A user may disconnect while the agent is sandboxing.

When reconnecting, the session should show:

```text
Previous state:

✓ Schema inspected
✓ Migration generated
✓ Sandbox validation passed
● Awaiting approval
```

The system must not:

- lose the migration plan
- silently re-run the destructive action
- double-apply the migration

Use TrueForge session state instead of inventing another session mechanism where possible.
